# 证据与版本策略

这本书不是对一篇论文的扩写，也不是对一个仓库的游览。它把不同时间、不同权威级别的材料组合成工程方法，因此首先要说明：什么是事实，什么是解释，什么是本书提出的工作模型。

## 四级证据

| 标签 | 含义 | 可支持的陈述 |
|---|---|---|
| E1 | 论文事实 | 论文明确报告的设计原则、测量、测试策略、部署观察与作者结论 |
| E2 | 源码及项目规则事实 | 固定 commit 中真实存在的代码、配置、测试、贡献规则和工具接口 |
| E3 | 生产与版本演化事实 | Ubuntu 官方迁移设计、事故记录、发布说明、安全审计与当前部署状态 |
| E4 | 本书方法提炼 | 基于 E1-E3 的命名、流程、检查表、架构判断和适用边界 |

E4 不能倒写为 E1。例如，“Agent 是约束下的实现搜索器”是本书对材料的抽象，不是论文中的原句；“AI-assisted contributions are allowed”来自论文之后的仓库规则，也不能写成论文的研究结论。

## 三条时间线

1. **论文测量线**：论文比较 GNU coreutils 9.9 与 uutils 0.4.0，并总结截至论文成稿期的部署与社区经验。
2. **源码核验线**：本书源码分析固定在 commit `d8bee62c1ddc227d5e4385d80bbf6d7dee266a41`，仓库版本描述为 `0.10.0-120-gd8bee62c1`。
3. **生产演化线**：Ubuntu 25.10 的默认迁移、2025 年 `date` 事故、2026 年安全审计和 Ubuntu 26.04 的部分 GNU 工具保留，按发生日期单独陈述。

任何“当前”都以 2026-08-14 为核验截止日。以后重建本书时，应重新核对 E2 与 E3，而不是直接保留“当前”措辞。

## 源码引用格式

正文使用固定 commit permalink，例如：

```text
uutils/coreutils@d8bee62c: AGENTS.md:7-23
```

每个分析过本地源码的章节还包含机器可检查的路径标记：

```html
<!-- source: AGENTS.md -->
```

路径标记只证明文件存在；行号和含义仍由事实审稿核验。禁止使用浮动 `main` 链接支撑会随版本变化的代码结论。

## Clean-room 规则

本书允许读取 uutils 的 MIT 许可实现、论文、规范、用户手册、黑盒输出和官方生产资料；不读取 GNU coreutils 实现代码，不复制其辅助结构、注释或测试夹具。这里的边界不只是许可证说明，也是 Agent 上下文的访问控制模型（详见第 4 章）。

## 推理纪律

- 单一来源只能证明它直接覆盖的事实。
- “之后发生”不等于“由此前事件导致”；因果链缺口必须明说。
- 测试通过率、依赖数、复杂度和贡献者数量使用论文口径时，必须同时给出论文版本与测量时间。
- Rust 的内存安全不等于语义正确、权限正确或无 TOCTOU；生产反例优先于语言宣传。
- 无法由一手来源确认的版本、日期或数字不进入正文。
